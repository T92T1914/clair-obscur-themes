# Windows Terminal colors

The Windows Terminal 0.1.0 candidate contains two color schemes, `Clair Obscur - Clair` and `Clair Obscur - Obscur`, in one JSON fragment. It adds named colors without supplying a profile, command, font, window layout or shell configuration. The fragment uses Windows Terminal's [supported scheme-extension format](https://learn.microsoft.com/en-us/windows/terminal/json-fragment-extensions). It is a separate candidate, with its own version and identities.

The package contains the JSON fragment and the project license. Its checksum and generator manifest are available beside the ZIP. No application is installed or configured by the generator. Native Windows Terminal loading, switching, restart persistence and restoration remain unverified.

## Build and inspect

From this repository, use Python 3.11 or newer:

```powershell
python -m themeforge.terminal --output outputs/terminal-02
python -m themeforge.terminal --output outputs/terminal-02 --check
```

Use a new output directory for a new build. The first command preserves any existing destination instead of overwriting it. The check compares every generated byte and required path without repairing a changed output.

The output is:

| File | Purpose |
| --- | --- |
| `Clair-Obscur-Windows-Terminal-0.1.0.json` | The schemes-only fragment to install manually |
| `LICENSE.txt` | The MIT grant to retain when sharing |
| `Clair-Obscur-Windows-Terminal-0.1.0.zip` | The fragment and license in a deterministic archive |
| `manifest.json` | Version, token mapping and file identities |
| `SHA256SUMS` | Checksums for the same generated set |

The JSON's only top-level member is `schemes`. Each of its two entries has a name, the 16 normal and bright ANSI colors, foreground, background, cursor color and selection background. These are color-table assignments. They do not color every shell or full-screen application automatically.

## Before a native trial

Use an authorized, recoverable test arrangement and record the exact Windows Terminal version and channel. Record the selected profile, its current `colorScheme`, Terminal application theme, any settings synchronization, and the existing fragment folder and filenames. Preserve the settings bytes privately as a recovery baseline. Avoid including shell history, commands, credentials or unrelated profile content in shared evidence.

Record any explicit profile `foreground`, `background`, `cursorColor`, `selectionBackground` and `unfocusedAppearance` values, along with font, size, intensity and opacity settings. These can alter the effective result. Do not reset them to obtain a cleaner-looking test.

Inspect existing schemes for both candidate names before installation. A matching name is a collision to resolve deliberately. The [Terminal loader](https://github.com/microsoft/terminal/blob/9fd41b2baec77d25b8cfb584070d5998eab7df81/src/cascadia/TerminalSettingsModel/CascadiaSettingsSerialization.cpp#L1134) can rename a different existing user scheme to a modified name and save settings during layering. A schemes-only fragment therefore does not guarantee that Terminal leaves the entire settings file byte-identical.

## Install manually

1. Verify the downloaded ZIP against the checksum from the same candidate. Extract it into an owned folder.
2. Locate the current user's `%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\ClairObscur\` folder. Create only this application subfolder if it is absent. Stop and inspect an existing same-name fragment rather than replacing it.
3. Copy only `Clair-Obscur-Windows-Terminal-0.1.0.json` into that folder. Keep the ZIP, license and identity files with the retained package. Do not copy the manifest or checksum into the fragment directory, whose JSON files Terminal reads.
4. Open Terminal Settings and inspect the chosen test profile's Appearance page. Select `Clair Obscur - Clair` or `Clair Obscur - Obscur` as its color scheme, then save through the host's normal control.
5. Confirm the effective result in the actual profile. An available scheme name alone does not establish that its colors reached the terminal pane.

The fragment folder is distinct from the installation-specific `settings.json` locations in the [official FAQ](https://learn.microsoft.com/en-us/windows/terminal/faq). Do not replace your entire settings file with this fragment, copy a real profile to an isolated fixture, change the default terminal application or install a shell to test these colors.

## Switch appearances

Select the other named scheme on the same test profile's Appearance page, save and inspect the same samples. Switch back once. Keep other profiles and the Windows appearance unchanged.

Windows Terminal 1.17 or later also supports a paired selection on an individual profile:

```json
"colorScheme": {
  "light": "Clair Obscur - Clair",
  "dark": "Clair Obscur - Obscur"
}
```

This is a setting for the chosen profile, separate from the downloadable fragment. Preserve the previous value before editing it. The pair follows the selected Terminal theme's application appearance. It follows the Windows appearance only when that application theme follows `system`. The [appearance contract](https://learn.microsoft.com/en-us/windows/terminal/customize-settings/profile-appearance) and [1.17 FAQ](https://learn.microsoft.com/en-us/windows/terminal/faq) describe this behavior. The package does not set an application theme or change the operating system.

A paired setting that parses is not an observed native switch. Check each permitted appearance in the real host. When an ordinary restart is separately allowed, observe persistence after that restart before making repairs.

## Colors and host controls

The default foreground uses the shared text role over the shared code background. Fourteen of the 16 ANSI foregrounds in each appearance have a calculated contrast of at least 4.5:1 against that opaque background. The exceptions are Clair's `white` and `brightWhite`, and Obscur's `black` and `brightBlack`. Those slots retain light and dark neutral roles so programs can use white-on-black combinations rather than receiving a table of foreground-only shades.

The four combinations of normal or bright white text on normal or bright black backgrounds also have calculated contrast of at least 4.5:1 in each appearance. The lowest is Obscur `white` on `brightBlack`, approximately 4.74:1. The reverse combinations have the same calculated ratios. These checks cover those specified pairs, not arbitrary ANSI foreground/background combinations. A program that puts white text on Clair's default light background, or black text on Obscur's default dark background, still needs an application-specific correction or setting.

Default text against the background and selection background is calculated at a 4.5:1 minimum. The cursor color against the default background is calculated at a 3:1 minimum. These are solid-color calculations. They do not establish native selected-glyph or cursor rendering, opacity behavior, color-vision distinctions, HDR output or complete accessibility conformance.

Applications choose which ANSI indexes they use and can supply explicit RGB or extended colors. A shell highlighter, PSReadLine configuration or full-screen program can therefore produce colors outside the scheme. Inspect a labeled normal and bright ANSI sample as well as ordinary text, selected text and the cursor. Keep any sample command local and do not post test messages or use private account content.

Profile-level color overrides take precedence over scheme values. `unfocusedAppearance`, `opacity`, `intenseTextStyle` and `adjustIndistinguishableColors` remain under host control. Intense text can use bright colors, bold, both or neither. A calculated color pair cannot establish which result a current profile uses.

The fragment keeps the existing monospace font and font size. Inter is used elsewhere in this theme family where it fits the application, but this candidate does not assign a proportional face to terminal cells. It includes no fonts. Native font fallback, ligatures, language and icon glyphs need their own actual-host observations.

## Remove and restore

1. Return the test profile to its recorded previous scheme or paired `colorScheme` value. Restore only the settings changed for this trial, including application appearance and any explicitly approved override changes.
2. Save and confirm that the prior appearance returns before removing the candidate.
3. Remove only the JSON fragment copied for this trial. Preserve a preexisting file and any Terminal-created or modified state until inspected. Leave unrelated fragments and profiles intact.
4. Reinspect the relevant settings and recorded fragment state. Compare the saved settings baseline and explain any differences rather than claiming full restoration from appearance alone.
5. Close only the test context when its restoration is complete. Record incomplete cleanup or restart checks explicitly.

This is scoped restoration, not a general Terminal reset. No installation, profile selection, restart or removal was performed by the source and package checks.

## Qualification boundary

Deterministic generation, exact field and color checks, official scheme-definition validation and a web specimen can qualify the package's source and format. They do not execute Terminal's native parser or establish native rendering.

Native acceptance remains `deferred-shared-pc`. It requires current scoped control, a working supported controller, the exact host identity and a recoverable baseline. The remaining journey is loading both schemes, default and normal/bright ANSI text, selection and cursor behavior, manual and paired switching where supported, persistence after an approved ordinary restart, and restoration of the recorded state.
